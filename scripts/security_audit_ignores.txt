# ── 2026-09-23 re-triage — the list is now empty ─────────────────────────────
# All 42 entries that stood here were re-verified against OSV and against the
# versions the repo actually resolves, rather than against the claims in their
# own reason strings. Every one of them was resolvable, so none was carried
# forward. Nothing is suppressed today.

# The entries were re-checked ahead of the 2026-10-05 ecdsa expiry because
# `load_ignores` fails closed: a lapsed entry aborts `validate-ignores` before
# any ecosystem is scanned, which reds every open PR and leaves `main`
# stale-green. That has happened here before (twelve expired suppressions,
# #650), so the list is re-read on a schedule rather than on a failure.
#
# Recording what was measured, because most of these reason strings had
# quietly stopped being true and re-reading them would have produced another
# round of date bumps rather than fixes:

#   • starlette (9 entries) claimed "slack-bot and teams-bot still cap fastapi
#     <0.137, which resolves fastapi 0.136.1 / starlette 1.0.0". Neither cap
#     exists: both pyproject files read fastapi >=0.111,<0.142 and both locks
#     resolve fastapi 0.141.1 with starlette 1.6.0. services/agents resolves
#     starlette 1.3.1. The highest fix among the nine is 1.3.1, so every
#     service was already clean.
#
#   • idna CVE-2026-45409 claimed "only services/slack-bot still resolves
#     3.13". slack-bot resolves 3.20, teams-bot 3.15, agents 3.18; the fix is
#     3.15. (The CVE id is also not a resolvable OSV record — OSV carries this
#     as GHSA-65pc-fj4g-8rjx / PYSEC-2026-215 with the CVE as an alias.)
#
#   • langchain / langgraph (9 entries) claimed pins of langchain <0.4.0,
#     langchain-openai <0.4.0 and langgraph <1.1.0 blocking a "0.3 to 1.x
#     migration". That migration has already happened: the pins read
#     langchain >=1.3.9, langchain-core >=1.2.22, langgraph >=1.0.10,
#     langgraph-checkpoint >=4.1.1, langgraph-sdk >=0.3.15, and the lock
#     resolves 1.4.2 / 1.6.4 / 1.2.12 / 4.2.0 / 0.4.5 respectively.

#
#   • langchain-core (4 entries) claimed the same blocked major bump. The lock
#     resolves 1.6.4; the fixes are 1.2.11 and 1.2.22.

#   • weasyprint (3) and anyio (5) claimed they were "pinned by the committed
#     services/agents lock, needs a lock refresh". That lock already carries
#     weasyprint 70.0 and anyio 4.15.1, which are the fixed versions.

#   • pydantic-settings claimed "slack-bot/teams-bot still resolve 2.14.1".
#     Both resolve 2.15.0; the fix is 2.14.2.

#   • cryptography (3 entries) claimed the fix was "held by the <50 and <49
#     version caps". No such cap exists anywhere — every pin reads <51 — and

#   • aiohttp (3 entries) claimed 3.14.1 awaiting a lock refresh; the locks
#     resolve 3.14.3, which is the fix. h2 claimed 4.3.0; agents resolves

# ── 2026-09-24 — apps/mobile, a second install root the audit never saw ──────
# The two image-size entries below look like the pair dismissed above and are a
# different case. That one was @docusaurus/mdx-loader holding ^2.0.2 in the root
# workspace, where 2.0.4 is a drop-in. This one is metro, and the fix really is
# out of reach:
#
#   • apps/mobile resolves image-size 1.2.1, pulled only by metro 0.83.3.
#   • No patched 1.x exists — 1.2.1 is the last 1.x and the fix landed in 2.0.3.
#   • Every metro release through the current latest (0.87.1) still declares
#     image-size ^1.0.2.
#   • metro/src/Assets.js calls the callable default export at lines 68 and 173
#     — `(0, _imageSize.default)(content)` — which image-size 2.x replaced with
#     named exports. An override here does not bump a version, it breaks asset
#     resolution at bundle time.
#   • Dependabot's own updater reaches the same verdict independently:
#     security_update_not_possible, latest-resolvable 1.2.1,
#     lowest-non-vulnerable 2.0.3, conflicting-dependencies [].
#
# Both advisories are denial of service only (CVSS A:H, C:N/I:N) via infinite
# loops in the JXL/HEIF and ICNS parsers. Reaching them needs a malicious image
# inside this repository's own asset tree, which presupposes commit access, and
# the impact is a hung developer bundler. No runtime, server or user-input path
# reaches this code.
#
# Why they were invisible rather than accepted is the part worth keeping:
# `pnpm audit` ran only at the repo root, and apps/mobile is a deliberately
# separate install root, so this arm reported a clean workspace while two high
# advisories stood open. run_pnpm_audit now discovers every directory holding a
# pnpm-lock.yaml, so a third install root is covered the day it appears rather
# than the day someone remembers it exists.
#
# Retire these when metro adopts image-size >= 2.0.3.
