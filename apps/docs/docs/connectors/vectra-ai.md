## Setup

1. In the console, go to **Connectors → Add connector** and pick **Vectra AI Platform**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

1. Sign in to your Vectra AI Platform console. Its address,
   `https://<id>.<region>.portal.vectra.ai`, is the **Portal URL**. Paste it
   without any path.
2. Go to **Configuration → Access → API Clients** and add an API client
   with a role that can read detections.
3. Copy the **Client ID** and the **Secret Key**. The secret key is shown
   once. Only the secret key goes into the credential vault; the client ID
   is an identifier.

The portal URL must use HTTPS. A bare host is read as `https://<host>`, and
an `http://` URL is refused before anything is sent, so the secret key never
crosses the network in clear.

The connector exchanges the client ID and secret key for an access token at
`POST /oauth2/token` (OAuth2 client credentials, HTTP Basic). It reuses that
token until shortly before it expires. If Vectra refuses a cached token
early, the connector exchanges the credential once more before failing the
poll.

## What is read

`GET /api/v3.4/events/detections`, the detection events stream. Every time
Vectra raises a detection against a host or an account, or updates one, it
adds an event to this stream.

The read starts at the beginning of the poll window (`event_timestamp_gte`),
500 events a page. While `remaining_count` says there are more, the
connector requests the next page from `next_checkpoint`. Each request is
built from the portal URL you configured, so the credential is never sent to
a host named in a response.

- If a later page fails, the pages already read are kept.
- If the token exchange or the opening request is refused or can't reach the
  portal, the poll fails instead of reporting a quiet network.
- A poll reads at most 25 pages. When there is still more, it logs
  `connector.paging.page_cap_reached`.

Detections in Vectra's `info` category are not requested.

**Each detection is raised once per poll.** The alert's `external_id` is the
Vectra `detection_id`, and when a poll reads several events for one
detection, only the newest becomes an alert. A detection that fires again in
a later poll carries the same `external_id`.

- An event stamped after the poll began is left to the next poll, whose
  window starts where this one ended.
- A detection a triage rule in Vectra has marked (`triaged: true`) is not
  raised. The triage rule already records that the behaviour is expected.

The detection's name becomes the alert title. The alert also keeps the
category, the portal link to the detection, the entity type and id, and the
MITRE ATT&CK technique ids. A host detection fills the host column and an
account detection fills the user column; neither fills the other. The whole
vendor record is kept under `raw_event`.

## Why there is no severity

Vectra does not score individual detections on this platform. Its own
guidance is that individual detections are no longer scored; prioritisation
happens on the host or account. A detection event still carries `threat`,
`certainty` and an integer `severity`, but the first two are legacy scores
that are often zero, and the third isn't documented.

So the connector emits no severity tier rather than guessing one in the
vendor's name. All three numbers stay in `raw_event` as Vectra sent them. The
ingest profile files `vectra_ai` as an OCSF Security Finding (class 2001),
which is promoted to an alert whatever its severity.

## Troubleshooting

| Test connection or the poll says | Meaning |
|---|---|
| `The portal URL must use HTTPS …` | The portal URL starts with `http://`. Use the `https://` address of the console. |
| `… HTTP 401 to POST /oauth2/token …` | The client ID or secret key is wrong, or the API client was deleted. |
| `… HTTP 403 to GET /api/v3.4/events/detections …` | The API client is valid, but its role can't read detections. |
| `Vectra could not be reached at …` | The connectors service has no route to the portal. Check the URL, the outbound proxy and the firewall rules. |
| `… HTTP 429 …` | The tenant's API rate limit is used up, often by another integration. The next poll retries. |
