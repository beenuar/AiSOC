WithSecure Elements EDR Broad Context Detections via the Elements API, each raised once with the host, user, process and MITRE ATT&CK techniques of its detections. Read-only.

- **Connector id:** `withsecure_elements`
- **Category:** edr

## Configuration

| Field | Label | Type | Required | Default | Notes |
|-------|-------|------|----------|---------|-------|
| `client_id` | Client ID | string | yes | — | From an API client created in Elements Security Center under Management > Organization Settings > API clients. |

| `organization_id` | Organization ID | string | no | — | The UUID of the organization to read. Leave empty to read the API client's own organization; a partner account sets the customer organization here. |

:::note Credential handling
`client_secret` is encrypted at rest by the credential vault before the row is written, and decrypted only at poll time. The value is never logged and never returned by the API — a read of the saved connector shows the field as set, not its contents. See [credential vault](../operations/credentials.md).
:::

## Setup

1. In the console, go to **Connectors → Add connector** and pick **WithSecure Elements**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

The connector signs in with an Elements API client: a client ID and secret
exchanged for a short-lived token. WithSecure's
[Getting started](https://connect.withsecure.com/getting-started/elements)
page walks through creating one:

1. Sign in to Elements Security Center with the **IAM Administrator** or
   **Elements Editing All** role.
2. Under **Management**, select **Organization Settings**, then
   **API clients** from the menu at the top.
3. A partner account switches the scope selector to the customer
   organization first.
4. Select **Add new**, enter a description, and leave **Read-only**
   selected. The connector only asks for the read scope, `connect.api.read`.
5. Copy the secret before you close the dialog. WithSecure shows it once.
6. Enter the client ID and secret in the connector. The secret is stored in
   the credential vault.

Leave **Organization ID** empty to read the organization the API client
belongs to. A partner reading a customer organization sets that
organization's UUID here.

There is no URL field. Every request goes to `https://api.connect.withsecure.com`,
so the secret is never sent anywhere but WithSecure.

## What is read

The connector exchanges the client ID and secret at
`POST /as/token.oauth2` with the client credentials grant and uses the token
until shortly before it expires. If WithSecure refuses a cached token early,
the connector exchanges once more; a freshly issued token that is refused
fails the poll instead of looping.

It then reads Elements EDR **Broad Context Detections** (BCDs), which the API
calls incidents: `GET /incidents/v1/incidents`, oldest first, 50 a page (the
documented maximum). It follows `nextAnchor` until WithSecure leaves it out. If a later page fails, the pages
already read are kept. If the opening request is refused or can't reach
WithSecure, the poll fails instead of reporting an empty window.

**Each BCD is raised once.** A BCD is updated every time a detection joins
it or an analyst touches it, so the poll window is applied to
`createdTimestamp` rather than `updatedTimestamp`. A BCD created after the
read began is left to the next poll. The connector keeps a cursor at the
newest `createdTimestamp` ingest has accepted and opens each poll's request
there rather than at the clock, so a poll cut short by the 25-page bound, or
a run of failed polls, is caught up by the next successful one. Catch-up
reaches back at most seven days.

WithSecure closes some BCDs by itself. One closed as `merged` is a duplicate
of the BCD it was merged into. One closed as `autoFalsePositive` or
`autoAcceptedBehavior` matched a false-positive mark or a suppression rule
your organization set. Those three aren't raised. Every other BCD is, open
or closed, with its status and resolution. Archived BCDs aren't filtered
out: WithSecure doesn't document when a BCD is archived, so a filter on it
could drop one created inside the window.

## What a BCD is made of

A BCD has a name, a severity and categories, but no host, user or process.
For each BCD in a poll, the connector reads its newest 100 detections
through `GET /incidents/v1/detections`. It looks up each distinct device
those detections name through `GET /devices/v1/devices`. The alert
carries:

- the BCD name as its title, its description, its public ID as shown in the
  portal, its status, resolution, risk score, categories and sources;
- the process, command line and executable hash of the BCD's most severe
  detection (the newest one among equally severe detections);
- the user and host of that detection, or of the first detection that names
  one when it doesn't;
- that host's name, first internal address, public address and operating
  system;
- every host and every MITRE ATT&CK technique and tactic across the
  detections, and the detection names.

The detections and device records are kept under `raw_event.detections`
and `raw_event.devices`, next to the rest of the vendor record. Each
detection is kept without its `activityContext`, which WithSecure leaves
open-ended. Leaving it out, and reading one page of detections, keeps the
size of each BCD's event bounded.

- A poll reads the detections of at most 50 BCDs, the most severe first.
  When there are more, it logs
  `withsecure_elements.detection_lookups_capped`.
- A poll looks up at most 50 devices, the host each BCD is filed on before
  the other hosts its detections name. When there are more, it logs
  `withsecure_elements.device_lookups_capped`.
- On HTTP 429, or when WithSecure stops accepting the credential part-way
  through a poll, the lookups of that kind stop for the poll, and
  `withsecure_elements.detection_lookups_stopped` or
  `withsecure_elements.device_lookups_stopped` is logged.

Every BCD is still returned either way. The ones whose lookups were skipped
or failed arrive without their host, user or process.

## Rate limit

WithSecure allows 300 requests a minute from one address to its EDR
endpoints, which cover the BCD, detection and device reads alike. The bounds
above keep a single poll to at most 125 requests. Other integrations calling
the Elements API from the same address share that limit.

## The severity ladder

| WithSecure `severity` | AiSOC severity |
|---|---|
| `critical` | `critical` |
| `high` | `high` |
| `medium` | `medium` |
| `low` | `low` |
| `info` | `info` |

`critical` stays `critical`. A BCD without a `severity` falls back to its
`riskLevel`, which uses the same names except that its top level is
`severe`, mapped to `critical`. A value WithSecure doesn't document carries
no severity rather than a guessed one.

The ingest service files `withsecure_elements` events as OCSF 2001 Security
Finding, so every BCD is promoted to an alert, whatever its severity.

## Troubleshooting

| Test connection or the poll says | Meaning |
|---|---|
| `… HTTP 400 to POST /as/token.oauth2 …` or `… HTTP 401 to POST /as/token.oauth2 …` | The client ID or secret is wrong, or the API client was deleted. |
| `… HTTP 403 to GET /incidents/v1/incidents …` | The API client is valid but may not read this organization. Check the organization ID. |
| `… HTTP 404 to GET /incidents/v1/incidents …` | The organization ID doesn't exist, or is outside this API client's scope. |
| `… HTTP 429 …` | The 300-a-minute EDR rate limit is used up, often by another integration on the same address. The next poll retries. |
| `WithSecure could not be reached at api.connect.withsecure.com` | The connectors service has no route to WithSecure. Check its outbound proxy and firewall rules. |
