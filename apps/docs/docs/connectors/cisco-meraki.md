# Cisco Meraki

Cisco Meraki MX security appliance events — intrusion detection alerts and files Advanced Malware Protection judged malicious — across every network in an organization, via the Dashboard API v1. Read-only.

- **Connector id:** `cisco_meraki`
- **Category:** network

## Configuration

| Field | Label | Type | Required | Default | Notes |
|-------|-------|------|----------|---------|-------|
| `region` | Dashboard region | select | yes | — | The Meraki dashboard the organization lives in. · one of: `global`, `canada`, `china`, `india`, `fedramp` |
| `organization_id` | Organization ID | string | yes | — | Shown at the foot of every dashboard page, and returned by GET /organizations. |
| `api_key` | API key | secret | yes | — | **encrypted at rest** · Generated under My profile → API access by an administrator of the organization. Read-only organization access is enough. |

:::note Credential handling
`api_key` is encrypted at rest by the credential vault before the row is written, and decrypted only at poll time. The value is never logged and never returned by the API — a read of the saved connector shows the field as set, not its contents. See [credential vault](../operations/credentials.md).
:::

## Capabilities

- `pull_alerts`

## Setup

1. In the console, go to **Connectors → Add connector** and pick **Cisco Meraki**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

1. In the Meraki dashboard, open **Organization → Settings** and make sure
   **Dashboard API access** is enabled for the organization.
2. Open **My profile → API access** and generate an API key. The key carries
   the permissions of the administrator who generated it, and the connector
   only reads, so an administrator with **read-only** access to the
   organization is enough. Meraki shows the key once.
3. Copy the **Organization ID**. It is shown in the footer of every dashboard
   page, and `GET /organizations` with the key lists it as `id`.
4. Pick the **Dashboard region** the organization lives in. It is the host of
   the dashboard you sign in to:

| Dashboard region | API host |
|---|---|
| `global` — most of the world | `https://api.meraki.com/api/v1` |
| `canada` | `https://api.meraki.ca/api/v1` |
| `china` | `https://api.meraki.cn/api/v1` |
| `india` | `https://api.meraki.in/api/v1` |
| `fedramp` — US FedRAMP | `https://api.gov-meraki.com/api/v1` |

There is no URL field. The dashboard may redirect a request to the shard that
serves the organization (for example `n149.meraki.com`); the connector follows
a redirect, and a next-page link, only to an HTTPS host inside the chosen
region's domain, so the API key is never sent anywhere but Meraki.

## What is read

`GET /organizations/{organizationId}/appliance/security/events`, authenticated
with `Authorization: Bearer <key>`: the security events of the MX appliances in
every network of the organization, from `t0` to `t1`, oldest first
(`sortOrder=ascending`), 1000 a page. The connector follows the response's
`Link: <…>; rel=next` header until it is absent or a page comes back empty, so
the window is read to the end; at most 25 pages are read in one poll, and the
bound is logged as `connector.paging.page_cap_reached` when it binds. A later
page failing keeps the pages already read.

Because the read is oldest first, a poll cut short — by the page bound, a 429
or a failed page — always stops at a point in time. The cursor rests on the
newest event raised and the next poll's window opens there, so the rest of the
burst is read then rather than skipped. The window also overlaps the previous
poll by one interval, which covers a run the scheduler skipped.

Meraki gives a security event no id. Each event's `external_id` is a digest
of the whole record as Meraki sent it, which is how an event re-read by an
overlapping window is recognised and dropped.

Each event's type and name become the alert title — for example
`IDS Alert: SERVER-WEBAPP JBoss JMX console access attempt`, or
`File Scanned: PUA.Win.Dropper.Kraddare::1201` with the malware name AMP gave
the file. The source and destination address and port, protocol, Snort
signature and rule id, client name and MAC, the appliance's MAC, the URL, the
file's SHA-256, type and disposition, and whether the appliance blocked it are
lifted onto the alert. The whole vendor record is kept under `raw_event`.

**Only events that rate as a threat are ingested.** The same list carries TLS
decryption failures (`TLS Decrypt Alert`), and a scanned file can come back
clean. This connector's events are filed as OCSF Security Findings (class
2001), which the fusion promoter turns into alerts unconditionally, so the
connector skips unrated events and logs how many, by type, as
`cisco_meraki.unrated_events_skipped`.

## The severity ladder

Meraki's intrusion detection runs Snort rules, and an `IDS Alert` carries the
rule's Snort `priority`, 1 being the most severe.

| Meraki event | AiSOC severity |
|---|---|
| `IDS Alert`, priority `1` | `high` |
| `IDS Alert`, priority `2` | `medium` |
| `IDS Alert`, priority `3` | `low` |
| `IDS Alert`, priority `4` | `info` |
| `File Scanned`, disposition `Malicious` | `high` |

Snort defines no level above its first, so nothing is raised as `critical`. A
priority outside the four carries no `severity` key rather than a guessed one.

## Troubleshooting

| Test connection says | Meaning |
|---|---|
| `… HTTP 401 to GET /organizations/…` | The API key is wrong or was revoked, or the region does not match the dashboard the organization lives in. |
| `… HTTP 403 …` | The key's administrator has no access to this organization. |
| `… HTTP 404 …` | The organization ID is wrong, Dashboard API access is disabled for it, or it lives in another region. |
| `… HTTP 429 …` | The organization's API rate limit is exhausted, often by another integration sharing it. The next poll retries. |
| `… a redirect to … which is not an HTTPS host of the … dashboard` | The dashboard redirected the request outside the region's domain, and the key was not sent there. |
| `region … is not a Meraki dashboard region` | The saved region is not one of `global`, `canada`, `china`, `india` or `fedramp`. |
