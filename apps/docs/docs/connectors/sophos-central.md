Sophos Central alerts — endpoint and server threats, exploit and ransomware protection, intrusion prevention — via the SIEM Integration API, with the data region discovered from the credential. Read-only.

- **Connector id:** `sophos_central`
- **Category:** edr

## Configuration

| Field | Label | Type | Required | Default | Notes |
|-------|-------|------|----------|---------|-------|
| `client_id` | Client ID | string | yes | — | — |
| `client_secret` | Client secret | secret | yes | — | **encrypted at rest** · Created in Sophos Central under Global Settings → API Credentials Management. |
| `tenant_id` | Tenant ID | string | no | — | Leave blank for a credential created inside the tenant. Required for a partner or organization credential, which can see many tenants: the ID of the tenant whose alerts this connector reads. |

:::note Credential handling
`client_secret` is encrypted at rest by the credential vault before the row is written, and decrypted only at poll time. The value is never logged and never returned by the API — a read of the saved connector shows the field as set, not its contents. See [credential vault](../operations/credentials.md).
:::

## Capabilities

- `pull_alerts`

## Setup

1. In the console, go to **Connectors → Add connector** and pick **Sophos Central**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

1. In Sophos Central, open **Global Settings → API Credentials Management**
   and add a credential. The connector only reads, so give it the
   least-privileged role your account offers.
2. Copy the **client ID** and **client secret**. The secret is shown once.
3. Leave **Tenant ID** blank. A credential created inside a tenant already
   names its tenant, and the connector asks Sophos which one it is.

There is no region or URL to enter. The connector exchanges the credential
at `https://id.sophos.com/api/v2/oauth2/token`, asks
`https://api.central.sophos.com/whoami/v1` who the credential belongs to,
and reads alerts from the data region host that answer names, such as
`https://api-eu01.central.sophos.com`. A host outside `sophos.com` is refused
rather than sent the token.

### Partner and organization credentials

A credential created at partner or organization (enterprise) level can see
many tenants, so Sophos cannot say which one to read. Set **Tenant ID** to
the ID of that tenant. The connector looks the tenant up through
`/partner/v1/tenants/{id}` or `/organization/v1/tenants/{id}` to find its
data region, then reads it with `X-Tenant-ID`. One saved connector reads one
tenant; add a connector per tenant to read several.

## What is read

`GET /siem/v1/alerts` — the alert half of the SIEM Integration API, the same
feed Sophos's own SIEM integration script reads. Each alert carries a
description, the threat name, the device name (`location`), the user Sophos
attributes it to (`source`) and the endpoint's address. These become the
alert's title, host, user and source IP in AiSOC; an intrusion-prevention
alert also carries the remote peer, which becomes the destination IP. The
whole vendor record is kept under `raw_event`.

The window is read to the end. Sophos returns at most 1,000 alerts a page
and says whether more follow with `has_more`; the connector follows
`next_cursor` until it says no.

**The API only looks back 24 hours.** `from_date` "must be within last 24
hours", and a request older than that is refused outright. A poll asking for
more — the scheduler's backfill after an outage can ask for a full day — is
shortened to just under 24 hours, and the connectors service logs
`sophos_central.window_shortened` when it happens. Alerts older than that
cannot be read through this API.

## The severity ladder stops at high, on purpose

Sophos publishes three alert severities — "must be one of: LOW, MEDIUM,
HIGH" — and no fourth.

| Sophos severity | AiSOC severity |
|---|---|
| `HIGH` | `high` |
| `MEDIUM` | `medium` |
| `LOW` | `low` |

**No alert from this connector is ever `critical`.** Promoting `HIGH` would
assert a tier Sophos does not publish, which is the same defect as
collapsing a vendor's real `critical` into `high`, in the other direction.
Nothing is lost by it: these alerts are filed as OCSF Security Findings
(class 2001, category 2), which the fusion promoter promotes to an alert
regardless of severity. A value outside the three carries no severity rather
than a guessed one, and is still promoted.

## Troubleshooting

| Test connection says | Meaning |
|---|---|
| `Sophos ID refused the client credentials` | The client ID or secret is wrong, or the credential was deleted or has expired. |
| `This is a partner credential …` / `This is an organization credential …` | Set **Tenant ID** to the tenant to read. |
| `This credential belongs to tenant …, not to the configured tenant …` | A tenant credential was given a different Tenant ID. Clear the field. |
| `… HTTP 403 to GET /siem/v1/alerts …` | The credential's role does not allow reading SIEM alerts for this tenant. |
| `… when looking up tenant …` | The partner or organization credential cannot see that tenant, or the ID is wrong. |
