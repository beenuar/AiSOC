Huntress Managed EDR incident reports — footholds, ransomware canaries, process, antivirus, identity and SIEM detections a Huntress SOC analyst has confirmed and delivered — via the v1 REST API, with the affected host resolved from its agent. Read-only.

- **Connector id:** `huntress`

|-------|-------|------|----------|---------|-------|

:::note Credential handling
`api_key`, `api_secret` are encrypted at rest by the credential vault before the row is written, and decrypted only at poll time. The value is never logged and never returned by the API — a read of the saved connector shows the field as set, not its contents. See [credential vault](../operations/credentials.md).
:::

## Setup

1. In the console, go to **Connectors → Add connector** and pick **Huntress**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

1. Sign in to the Huntress portal at `<your subdomain>.huntress.io` and open
   **API Credentials** (Huntress's
   [Generating API Keys](https://support.huntress.io/hc/en-us/articles/4416826761235-Generating-API-Keys)
   article walks through it).
2. Generate a credential and copy the **API Key** and the **API Secret Key**.
   The secret key is shown once.
3. Paste both into the connector. Both are stored in the credential vault.

The credential reads with the role of the user who generated it. That user
must be able to see incident reports and agents. A role that can't answers
HTTP 403.

The API lives at one host, `https://api.huntress.io`, for every account.
There is no URL field, so the credential is never sent anywhere else.

## What is read

`GET /v1/incident_reports`, authenticated with HTTP Basic (API key and
secret key). An incident report is what a Huntress SOC analyst sends after
confirming a threat: a foothold, a tripped ransomware canary, a malicious
process, an antivirus or identity detection. Each one becomes an alert.

The list endpoint has no time filter, so the connector reads it sorted by
`updated_at`, newest first, 500 reports a page (the documented maximum). It
follows `pagination.next_page_token` until a page reaches reports last
updated before the poll window opened. If a later page fails, the pages
already read are kept. If the opening request is refused or can't reach
Huntress, the poll fails instead of reporting an empty window. The next page
is requested with the token, not taken from `next_page_url`, so a host named
in a response never receives the credential.

**Each report is raised once, when it is delivered.** The poll window is
applied to `sent_at`, the moment the Huntress SOC sent the report.

- A report that is later closed, commented on or remediated is updated
  again, but it isn't raised again.
- A report Huntress never sent (dismissed before delivery) isn't raised.
- A report sent while a poll is running is left to the next poll, whose
  window starts where this one ended.

The report's subject becomes the alert title and the analyst's summary
becomes its description. The status, platform, indicator types, agent id
and organization id are kept. The whole vendor record is kept under
`raw_event`.

## The host behind a report

A report names its host only by agent id. For each distinct agent in a
poll's reports, the connector calls `GET /v1/agents/{id}` once. It lifts the
agent's hostname, internal IP, external IP and operating system onto the
alert, and stores the agent record on the report under `raw_event.agent`.

Huntress limits every account to **60 requests a minute**, and the lookups
count against that limit along with the list read. So:

- A poll looks up at most 20 agents. When there are more, it logs
  `huntress.agent_lookups_capped`.
- On HTTP 429 the lookups stop early and `huntress.agent_lookups_rate_limited`
  is logged.

Either way, every report is still returned. The ones whose agent wasn't
looked up arrive without a host. Reports on Microsoft 365, Google or email
security carry no agent at all.

## The severity ladder

| Huntress severity | AiSOC severity |
|---|---|
| `critical` | `critical` |
| `high` | `high` |
| `low` | `low` |

Huntress publishes no medium tier, and `critical` stays `critical`. It is
never collapsed into `high`.

## Troubleshooting

| Test connection or the poll says | Meaning |
|---|---|
| `… HTTP 401 to GET /v1/account …` | The API key or secret key is wrong, or the credential was revoked. |
| `… HTTP 403 to GET /v1/incident_reports …` | The credential is valid, but its user's role can't read incident reports. |
| `Huntress could not be reached at https://api.huntress.io: …` | The connectors service has no route to the API. Check its outbound proxy and firewall rules. |
| `… HTTP 429 …` | The account's 60 requests a minute are used up, often by another integration sharing the account. The next poll retries. |
