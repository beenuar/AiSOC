Cisco Secure Endpoint (formerly AMP for Endpoints) detections — threats, quarantines, exploit prevention, behavioural protection, indicators of compromise and threat hunting incidents — via the v1 events API. Read-only.

- **Connector id:** `cisco_secure_endpoint`
- **Category:** edr

## Configuration

| Field | Label | Type | Required | Default | Notes |
|-------|-------|------|----------|---------|-------|
| `region` | Region | select | yes | — | The Secure Endpoint cloud the console and the API credential live in. · one of: `nam`, `eu`, `apjc` |
| `client_id` | API client ID | string | yes | — | — |
| `api_key` | API key | secret | yes | — | **encrypted at rest** · Created in the Secure Endpoint console under Accounts → API Credentials. Read-only scope is enough. |

:::note Credential handling
`api_key` is encrypted at rest by the credential vault before the row is written, and decrypted only at poll time. The value is never logged and never returned by the API — a read of the saved connector shows the field as set, not its contents. See [credential vault](../operations/credentials.md).
:::

## Capabilities

- `pull_alerts`

## Setup

1. In the console, go to **Connectors → Add connector** and pick **Cisco Secure Endpoint**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

1. In the Secure Endpoint console, open **Accounts → API Credentials** and
   choose **New API Credential**. The connector only reads, so leave the
   scope at **Read-only**.
2. Copy the **3rd party API client ID** and the **API key**. The key is
   shown once.
3. Pick the **Region** your console lives in. It is the host in the
   console's address bar:

| Console | Region | API host |
|---|---|---|
| `console.amp.cisco.com` | North America | `https://api.amp.cisco.com` |
| `console.eu.amp.cisco.com` | Europe | `https://api.eu.amp.cisco.com` |
| `console.apjc.amp.cisco.com` | Asia Pacific, Japan and China | `https://api.apjc.amp.cisco.com` |

A credential exists in one region only, and the others refuse it with HTTP
401. There is no URL field: the host is one of these three, so the API key
is never sent anywhere else.

## What is read

`GET /v1/events`, authenticated with HTTP Basic (client ID and API key),
from `start_date` at the start of the poll window. Cisco returns at most 500
events a request, newest first; the connector asks for the next 500 by
`offset` until a page comes back short, so the window is read to the end. A
later page failing keeps the pages already read. The next page is built from
the configured region rather than taken from `metadata.links.next`, so a
host named in a response is never sent the credential.

Each event's type and detection name become the alert title — for example
`Threat Detected: W32.Auto:12081e6ca3.in03.Talos`, or the indicator's short
name for a `Cloud IOC` and the incident title for a threat hunting incident.
The computer's hostname, user and first internal address, the file name,
path, SHA-256 and disposition, the remote address of a network event, and
the ATT&CK technique ids Cisco attaches are lifted onto the alert. The whole
vendor record is kept under `raw_event`.

**Only events Cisco rates are ingested.** The events stream also carries
operational records — policy updates, scans started and completed, file
fetches, installs — and Cisco leaves those without a severity. This
connector's events are filed as OCSF Security Findings (class 2001), which
the fusion promoter turns into alerts unconditionally, so an unrated policy
update would reach the alert queue. The connector skips them and logs how
many as `cisco_secure_endpoint.unrated_events_skipped`.

## The severity ladder

| Cisco severity | AiSOC severity |
|---|---|
| `Critical` | `critical` |
| `High` | `high` |
| `Medium` | `medium` |
| `Low` | `low` |

`Critical` — which Cisco sets on, among others, threat hunting incidents and
the gravest indicators of compromise — stays `critical` and is never collapsed into
`high`.

## Troubleshooting

| Test connection says | Meaning |
|---|---|
| `… HTTP 401 to GET /v1/events …` | The client ID or API key is wrong, the credential was revoked, or the region does not match the console the credential was created in. |
| `… HTTP 429 to GET /v1/events …` | The organisation's API rate limit is exhausted, often by another integration sharing it. The next poll retries. |
| `region … is not a Cisco Secure Endpoint region` | The saved region is not one of `nam`, `eu` or `apjc`. |
