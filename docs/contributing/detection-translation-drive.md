# Detection translation drive

This is the most parallelisable contribution surface in the project, and the
one where a first-time contributor can land something measurable in an hour.

## The gap, in the project's own numbers

From [`docs/detections/truth-table.md`](../detections/truth-table.md), which is
generated by `scripts/detection_truth_table.py` and CI-gated so it cannot
drift:

| tier | on disk | executable |
|------|--------:|-----------:|
| native | 869 | 869 |
| sigma (imported) | 3132 | 77 |
| splunk (imported) | 2005 | 0 |
| chronicle (imported) | 877 | 0 |
| car (imported) | 99 | 0 |

**947 of 6,983 rules fire today.** The other 6,036 are on disk for provenance
and ATT&CK coverage mapping, quarantined because their body is an upstream
query language the engine does not execute.

The project is deliberately honest about this — the README quotes the
executable figure, not the on-disk one. The way to improve the number is to
translate rules, not to relabel them.

## Start with Sigma

Of the five tiers, the imported Sigma pool is by far the best target:

- **3,055 quarantined Sigma rules**, against 77 already translated — so there
  are worked examples in-tree to copy from.
- Sigma's `selection` / `condition` model maps closely onto the native
  `match_when` DSL. It is mechanical, not a rewrite.
- SPL, YARA-L and CAR pseudocode need semantic reinterpretation and are a much
  poorer first task. Leave those.

## What a translation looks like

1. Pick a rule under `detections/_quarantine/` in the sigma tier. Check no open
   PR already claims it.
2. Translate the body into the native condition DSL. The 869 rules under
   `detections/<category>/` are your reference, and the 77 already-translated
   Sigma imports are the closest analogues.
3. Write **both** fixtures under `detections/fixtures/` — one event the rule
   must fire on, one it must stay quiet on. This is not optional paperwork: the
   gate replays both and a rule that fires on its negative fixture is rejected.
4. Move the rule out of `_quarantine/` into its category directory.
5. Open a PR. `validate-detections.yml` replays every fixture and
   `detection_truth_table.py --check` updates the counts.

## Why the negative fixture is the important one

A detection that fires on everything has perfect recall and no value. The
negative fixture is what stops the corpus filling with rules that would drown
an analyst, and it is the reason this drive can accept contributions from
people who have never seen the codebase: **the gate is objective**. Either the
rule fires on the positive and stays quiet on the negative, or CI says no.

## Scope one PR sensibly

One to five related rules. A 200-rule PR cannot be reviewed meaningfully and
will sit. A handful of rules covering one technique is a good unit, and it is
fine for that to be your whole contribution.

## If you want something smaller first

- Add a negative fixture to an existing native rule that has only a positive one.
- Fix a false positive someone has already reported against a firing rule.
- Pick up an issue labelled [good first issue](../../issues?q=is%3Aopen+label%3A%22good+first+issue%22).
